# Restore legacy TBank adapter behavior and unify resolver errors

**Date:** 2026-06-09 00:13
**Files:** `laravel_app/app/Modules/BrokerGateway/Providers/TBank/Infrastructure/Adapters/LegacyTBankProviderConfigAdapter.php`, `laravel_app/app/Modules/BrokerGateway/Core/BrokerApiSettingsResolver.php`, `laravel_app/tests/Unit/BrokerGateway/Providers/TBank/Infrastructure/Adapters/LegacyTBankProviderConfigAdapterTest.php`, `laravel_app/tests/Unit/BrokerGateway/Core/BrokerApiSettingsResolverTest.php`
**Severity:** medium

## Problem

После внедрения broker-aware runtime-резолва были выявлены два замечания:
- legacy-метод `LegacyTBankProviderConfigAdapter::resolve()` перестал гарантировать TBank и мог взять "первого провайдера" из конфига;
- `BrokerApiSettingsResolver` не всегда возвращал предсказуемый тип ошибки, если runtime-конфиг провайдера был поврежден.

## Root Cause

- Legacy-метод был переведен на `resolveForBroker(new Broker)` без явного `provider_code`, что задействовало fallback-логику `BrokerProviderCodeResolver`.
- В `BrokerApiSettingsResolver` оборачивался только вызов `factory->make(...)`, но ошибки при чтении runtime-параметров (`base_url`, `timeout`) могли выбрасываться ниже как `InvalidArgumentException`.

## Solution

- В legacy-методе явно задан `provider_code='tbank'` перед вызовом `resolveForBroker`, что вернуло исходный контракт поведения.
- В `BrokerApiSettingsResolver` весь runtime-резолв (создание + чтение параметров провайдера) заключен в единый `try/catch` с оберткой в `RuntimeException`.
- Добавлены `[FIX]`-логи:
  - debug для входа/успешного завершения legacy resolve;
  - warning при ошибке runtime-резолва с контекстом `provider_code`.

## Prevention

- Для legacy bridge-методов фиксировать явный контракт выбора провайдера и покрывать его отдельным тестом.
- При введении фасадного резолвера сразу унифицировать тип ошибок на границе сервиса.
- Проверять обратную совместимость старых API/adapter-сигнатур отдельным регрессионным тестом.
